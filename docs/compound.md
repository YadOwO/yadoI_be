## 软删除项目里，外键的级联规则永远不会触发

`items.category_id` 上写了 `on delete set null`，但本项目业务数据一律软删除、只更新
`deleted_at`，从不执行 `DELETE` 语句，因此这条级联规则在正常业务流程中永远不生效。

曾因此产生实际 bug：删除分类的接口只写了 `deleted_at` 就返回，物品继续挂在已删除的分类上，
与接口文档「该分类下的物品会被置为未分类」不符，客户端按文档写逻辑会读到悬挂引用。

**做法**：软删除路径下的所有引用清理都必须在代码里显式写，并与软删除放在同一个事务里，
否则中途失败会留下悬挂引用。清理时被更新的行 `updated_at` 会同步刷新，
使最后修改时间准确反映归属变化。

表上仍保留 `on delete set null`，作用仅限于防御有人手工执行物理删除，不能当作业务逻辑的保障。
将来新增引用 `categories` / `items` 的表时，同样要在软删除路径里手写清理。

## 本地库纳入迁移管理后，不能再混用 db:push

`db:push` 直接比对 `schema.ts` 与数据库并执行 DDL，**不写入迁移记录**；`db:migrate` 则依据
`drizzle/` 下的文件逐个应用并记录到 `__drizzle_migrations`。两者混用会让本地库的实际结构与
迁移历史脱节，之后 `db:generate` 算出的差异是错的——它以最后一个快照为基准，而库已被 push
改过。

曾因此埋下隐患：初期用 push 建表、没有生成任何迁移文件，代码进了仓库但生产执行 `db:migrate`
时无文件可应用，表一张都不会建，首次请求即 `relation does not exist` 报 500。

**做法**：表结构变更统一走 `db:generate` + `db:migrate`，本地也一样，不再用 `db:push`。
`drizzle/` 目录下的 SQL 与 meta 必须提交进 git，它们是表结构的版本历史而非构建产物。

补救已有的 push 结果时，若表中无数据，最干净的方式是生成迁移后 drop 掉再 migrate 重建——
这同时验证了迁移文件真能建出正确结构，否则它到生产第一次执行才知道对不对。注意迁移首句是
`CREATE SCHEMA`，需连 schema 一并 drop。
